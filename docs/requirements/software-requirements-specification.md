## 第一章 引言

### 1.1 编写目的

本说明书用于明确个人博客系统需要提供的功能、业务约束、数据和外部交互，以及可以验证这些要求的验收条件。它为后续需求评审、原型与设计核对、测试计划和真实变更提供统一输入，面向项目负责人、课程指导教师及承担开发、测试和文档工作的人员。

本项目已完成主要编码，正式需求文件在代码之后建立。因此本文是基于现有系统的回顾性整理，不证明开发前已经开展访谈、召开需求会议或确认基线。现有行为与拟定目标分别标注，不通过文档编写自动批准代码变更。

### 1.2 项目背景

个人博客需要持续发布和展示文章，读者需要检索内容、表达观点，管理员需要维护文章、用户和互动内容。课程项目据此构建简化版WordPress式PC Web系统，包含公开博客、注册用户功能和后台管理，形成文章发布—阅读—互动—审核的业务闭环。课程方法研究和后续全流程Skill属于过程成果，不是博客网站的业务功能。

### 1.3 系统范围

本期批准范围由14个业务模块组成，涵盖认证、邮箱重置密码、首页与介绍、文章查询与详情、点赞、评论与审核、留言与审核、个人资料、后台统计、文章管理、分类标签、用户管理和站点配置。对应40条功能需求、16条非功能需求、24条业务规则，编号直接沿用[需求清单](requirements-inventory.md)。

不将以下未实现功能纳入当前能力：评论回复/嵌套、通知中心、用户自行编辑或删除评论留言、邮箱注册验证、个人邮箱修改、前台投稿、用户删除、回收站恢复、封面本地上传、第三方登录、Token刷新及云文件存储。首页独立置顶区、公开评论分页/图片头像已明确本期暂缓，作为后续版本候选；服务器主动注销已按Q03明确本期暂缓，不在本文擅自增设功能编号。

### 2.2 用户角色

游客可浏览公开页面、注册、登录和找回密码。USER必须账号正常、未删除且身份有效，才可操作个人中心、点赞、评论和留言。ADMIN拥有这些能力并能进入后台；可以管理他人文章，不存在“仅本人文章”的管理员范围限制。管理员不得改自己的角色或禁用自己。

禁用不是新的用户角色。禁用用户仍可按游客浏览公开接口，历史通过评论、留言及点赞关系不删除，但不能登录或使用受保护操作。普通用户不能进入后台；游客受保护请求返回401，普通用户后台请求返回403。完整矩阵见配套角色文件第2节。

### 3.1 M01 用户认证与访问控制

#### BLOG-F-001 普通用户注册

- 基线范围：本期正式需求基线；批准优先级：Must（2026-10-08用户12.5-D批准）。

- 功能描述：系统应接受用户名、邮箱、密码和确认密码，建立普通用户账号，无需另填昵称。
- 使用角色：游客。
- 前置条件：用户未登录，账号信息未被占用，注册服务可用。
- 触发条件：点击注册提交。
- 正常业务流程：输入四项信息→检查非空、邮箱格式、密码长度与一致性→检查账号邮箱唯一→创建正常普通账号→返回资料→提示成功并切换登录页签，不自动登录。
- 异常处理：格式错误、空白、密码不一致、用户名/邮箱重复拒绝；失败不进入已登录状态。
- 后置条件：成功后账号为USER/ACTIVE，展示名来自用户名，密码非明文；失败不产生有效新账号。
- 验收标准：合法未占用用户名30/31/50字符可注册并随后登录，51字符拒绝；重复、新密码7/65个Unicode码点和不一致拒绝，夹带ADMIN/DISABLED不能覆盖固定赋值。不新增最小长度/字符限制。 第二批补充：新密码7/65个Unicode码点拒绝；8/64码点且≤72个UTF-8字节可通过长度校验；≤64码点但>72字节拒绝；恰好72字节不因字节长度被拒绝；超限不截断，三设置入口一致且后端独立拒绝绕过前端的输入；规则上线不自动改变旧哈希或强制重置，旧密码登录兼容单独回归。均为待设计、未执行验收，不等于满足其他业务条件。
- 当前实现状态：部分；注册代码存在，最大50字符与登录30字符不一致。证据E02/E16。
- 确认与待定：Q19仅指定范围已确认；待设计/核实：Java/JavaScript码点与UTF-8统计、Unicode规范化是否需处理、旧账号兼容回归、现存超限密码数量和错误逐字文案；阈值、码点口径、超限拒绝及保留旧哈希兼容原则已于12.4-C确认，不再待批准。不得自行规范化、转换、预哈希或更换算法。 Q01最大50已定，Q13指定规范化范围已确认，残余兼容策略待设计。

- 第二批指定目标：Q19：新密码须同时满足8—64个Unicode码点及UTF-8编码后不超过72字节；超出任一限制明确拒绝，不静默截断。适用于注册、登录状态下修改密码及邮箱验证码重置；前后端口径一致，后端独立校验。保留已有账号及密码哈希，不批量强制重置；已有密码登录验证不得直接套用新密码设置限制，不静默修改、截断或重新编码原密码，成功登录后可建议主动更新。

- 横切确认范围（Q12）：实际保存/更新失败不能报告成功，应明确反馈；该子范围已确认，其余业务范围仍按本条原确认状态。验收补充：故障时不展示成功，不以HTTP返回完成代替实际业务写入；用例待设计/未执行。

- 12.4-E指定确认：新注册/真实修改邮箱入口去首尾空格并统一小写，唯一性按规范化结果判断；注册/修改用户名去首尾空格，保留大小写，不新增字符集限制，最大50沿用Q01。历史账号不自动合并、批量改值、删除或重命名；冲突先审计再提交方案。

#### BLOG-F-002 用户与管理员登录

- 基线范围：本期正式需求基线；批准优先级：Must（2026-10-08用户12.5-D批准）。

- 功能描述：系统应验证用户名密码，向正常账号提供访问令牌和脱敏用户资料。
- 使用角色：持普通用户或管理员账号的游客。
- 前置条件：存在未删除且正常账号；正常流程使用正确凭证。

#### 密码字符与编码字节的区别

SecurityConfig创建BCryptPasswordEncoder；Boot 3.3.5依赖管理及本地实际crypto JAR对应Spring Security 6.3.4。注册、改密和邮箱重置的新密码按@Size 8—64；登录仅非空及max64，当前密码非空无Size。现有字符计数是字符串长度校验，不等于UTF-8字节数。依赖静态核查见[Q19影响分析](confirmed-requirements-impact-analysis.md#11-q19-密码字符长度与编码字节边界)：首72字节有效处理边界及未显式拒绝超长输入是技术现状；12.4-C已将新密码UTF-8≤72字节明确为目标，尚未实现。本轮无编码实验；禁止将静态事实写成测试通过。

待设计/核实：Java/JavaScript码点与UTF-8统计、Unicode规范化是否需处理、旧账号兼容回归、现存超限密码数量和错误逐字文案；阈值、码点口径、超限拒绝及保留旧哈希兼容原则已于12.4-C确认，不再待批准。不得自行规范化、转换、预哈希或更换算法。 登录前不直接套用新密码8—64码点及72字节限制；现有LoginRequest密码max64需纳入兼容设计，不默默增加登录最低8码点。

### 6.2 前后端HTTP交互

业务接口以`/api`开头，通常使用JSON请求和响应，头像上传例外。Axios开发基址为`/api`，默认超时10秒；这只是客户端配置，不是服务响应性能达标证据。受保护请求携带`Authorization: Bearer <token>`，公开、注册和登录请求不要求Token。Q02要求附带登录状态查询401不得强制中断公开阅读，但该请求本身仍须返回未授权而非开放个人数据。

统一业务响应由`code`、`message`和必要时的`data`组成；成功业务码为0。由于空字段序列化设置，某些无返回数据或错误响应可以不包含`data`，不能要求始终返回`data: null`。现有成功接口通常使用HTTP 200，不虚构创建接口统一采用201。分页结果包含记录和分页信息，公开评论是列表而不是分页对象。

### 6.3 数据库交互

后端通过MyBatis Plus与MySQL连接，浏览器不得直接连接数据库。连接地址、账号由运行配置提供，密码必须通过环境变量。数据库约束与业务检查共同保护关系和唯一性；逻辑删除查询须排除失效记录。涉及审核、关系更换、改密等流程的原子性应通过失败与并发测试确认，不仅依据事务标记判定。

初始化脚本和迁移脚本的适用对象须区分：新库使用结构及初始化脚本；已有库升级按现有结构选择迁移，不得重复添加列或灌入种子数据。具体路径见第七章。

### 6.4 邮件服务

系统通过SMTP发送重置验证码。账号、授权码等通过环境变量配置；公开联系邮箱与SMTP认证账号是不同用途。邮件应说明验证码、5分钟有效期和保密提醒；前端只收到发送结果，不通过响应获知验证码。

邮件未配置、投递失败、未注册邮箱、禁用账号或发送过频应得到明确失败。是否收到真实邮件须另作外部依赖测试；发送成功后外部邮件不随数据库事务回滚，不能承诺投递与数据库写入严格原子。参见Q04。

### 6.5 图片上传与访问

上传采用`multipart/form-data`，字段名`file`，浏览器自动生成boundary，不用JSON或Base64保存图片。用户身份由登录上下文确定，不接受他人ID。

头像默认存入后端运行目录下`uploads/avatars/`，可由`AVATAR_UPLOAD_DIR`调整物理目录。数据库保存`/uploads/avatars/{UUID}.{ext}`；该访问路径由静态映射公开读取，图片响应为文件内容而不是Result。开发前端代理`/uploads`，部署须提供同等访问能力，不能把开发代理当作已有生产部署。

旧受管头像仅在新资料提交后安全删除；外部资源和默认头像不删除。无头像及加载失败继续显示用户名首字。封面仍为外部URL，不扩大为封面上传功能。

### 6.6 JWT认证接口约定

登录返回访问令牌，客户端保存并为受保护请求附加Bearer头。服务端验证签名、有效期和Token版本，再查询当前有效账号与角色。JWT保存用户ID以及用户名、角色、版本等声明，但权限以数据库现状为准。

公开接口、发码和重置无需已有登录。无效Token访问受保护资源401，普通用户后台403。当前注销仅清客户端状态，无刷新Token或服务器注销接口；Q05已确认邮箱重置也须废旧Token但当前未实现；Q03已确认禁用永久废旧Token、启用后重新登录，本期暂不增加服务器主动注销；现有仅改status尚不符合目标。

## 第七章 数据需求

### 7.1 主要数据实体与约束

数据库以`schema.sql`的10张表为依据；本文只描述需求相关约束，完整字段定义仍以实际SQL为准。独立实体主要使用BIGINT UNSIGNED自增主键，关系表使用联合主键。字符集utf8mb4，InnoDB支持外键。

| 实体/实际表 | 关键数据与约束 | 业务用途 |
| --- | --- | --- |
| 用户 `sys_user` | username VARCHAR(50)、email VARCHAR(100)分别唯一；password保存BCrypt；avatar可空；role、status、token_version；created_at/updated_at/deleted | 账号、当前权限与资料；客户端不得返回密码 |
| 邮箱验证码 `email_verification_code` | email、code CHAR(6)、type、expire_time、used、create_time；没有deleted字段 | 用途、有效期及一次使用校验；不通过公开接口查询码 |
| 分类 `blog_category` | name VARCHAR(50)唯一、description、sort_order、status、时间及deleted | 每篇文章的一项分类与筛选 |
| 标签 `blog_tag` | name VARCHAR(50)、slug VARCHAR(80)分别唯一，description、status、时间及deleted；无排序列 | 多标签组织，停用与引用检查 |
| 文章 `blog_article` | title VARCHAR(200)、slug VARCHAR(220)唯一、summary VARCHAR(500)、LONGTEXT content、cover_url、category_id、author_id、status、is_top、阅读/点赞/评论数、published_at、时间及deleted | 文章及公开可见性、排序和统计 |

不是所有表都有逻辑删除字段；验证码、关联、点赞、配置的处理不能统一表述为逻辑删除。用户名实际列宽不解决登录参数上限差异；唯一键约束下被逻辑删除记录仍可能占用值。

### 7.2 数据关系

用户与所写文章、评论、留言分别一对多；分类与文章一对多；文章与标签通过关联表多对多；用户与文章通过点赞表多对多；文章与评论一对多。验证码通过邮箱与账号作业务匹配，没有用户外键；站点配置独立存在。

文章的分类和作者、评论的文章和用户、留言的用户使用物理删除RESTRICT关系；文章标签及点赞使用物理删除CASCADE。CASCADE仅在物理删除触发，文章逻辑删除不会自动清评论或点赞。文章标签由当前删除业务显式清理。

关系图及证据见[角色与业务流程](roles-and-business-flows.md)中的数据关系说明和[结构SQL](../../blog-server/src/main/resources/schema.sql)。若后续绘制ER图，应包含10实体；验证码与用户应标为邮箱业务关联，不画成数据库外键。

## 12.4-C Q19与Q15细化同步（阶段历史；规则继续有效，当前状态以12.5-C为准）

### Q19细化：新密码设置与旧账号验证分离

确认来源：2026-10-08用户ChatGPT请求12.4-C第三节。新密码须同时满足8—64个Unicode码点及UTF-8编码后不超过72字节；超出任一限制明确拒绝，不静默截断。适用于注册、登录状态下修改密码及邮箱验证码重置；前后端口径一致，后端独立校验。保留已有账号及密码哈希，不批量强制重置；已有密码登录验证不得直接套用新密码设置限制，不静默修改、截断或重新编码原密码，成功登录后可建议主动更新。

“Unicode码点”不等于Java String.length()或JavaScript字符串.length的UTF-16单元，也不等于用户肉眼看到的字形数量；组合字符可能有多个码点。码点和UTF-8字节两个条件必须同时满足。本次未增加ASCII限定、密码自动trim、规范化、预哈希、算法迁移或字符组合强度规则。

已找到的新密码设置入口只有注册、登录状态改密、邮箱重置三条；SQL演示哈希初始化不是新增交互设置入口。旧账号登录及修改密码中的当前密码验证保持原哈希验证兼容，不先套用新密码设置长度条件。尤其LoginRequest现有password max64的UTF-16限制应纳入兼容设计审查，不因本次规则再收紧登录。成功登录后可建议用户更新，而非强制更新或自动重编码。

验收目标（待设计、未执行）：新密码7/65个Unicode码点拒绝；8/64码点且≤72个UTF-8字节可通过长度校验；≤64码点但>72字节拒绝；恰好72字节不因字节长度被拒绝；超限不截断，三设置入口一致且后端独立拒绝绕过前端的输入；规则上线不自动改变旧哈希或强制重置，旧密码登录兼容单独回归。均为待设计、未执行验收，不等于满足其他业务条件。
