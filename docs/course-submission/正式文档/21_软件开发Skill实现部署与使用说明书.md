## 第二章 源码组织与入口实现

### 2.1 实际结构

```text
skill/software-development-workflow/
├─ SKILL.md
└─ references/
   ├─ 项目启动与需求理解.md
   ├─ 需求分析与变更管理.md
   ├─ 原型设计.md
   ├─ 系统总体设计.md
   ├─ 系统详细设计.md
   ├─ 编码实现.md
   ├─ 测试设计与验证.md
   ├─ 问题修复与回归.md
   ├─ 交付与维护.md
   ├─ 质量门与确认规则.md
   └─ 输出模板与证据规范.md
```

该目录共12份Markdown，即1入口、9阶段、2公共文件；没有独立脚本、资源包或`agents/openai.yaml`。博客的两个前端测试脚本属于应用案例，不属于Skill源码包。部署目录具有相同12个相对文件，因此物理上两份包有24个文件，但权威Skill源码成果只计12份。

### 2.2 SKILL.md的作用

入口YAML包含实际`name: software-development-workflow`和英文`description`，描述针对具体软件项目的规划实现、诊断修复、需求变更及生命周期文档，并排除无关写作与一般聊天。正文声明v0.1.0及中文说明要求，没有另设必需的YAML版本字段。

正文依次提供启动读取规则、任务路径表、九阶段引用表及授权停止摘要。它告诉执行者何时读取参考文件，不包含全部阶段正文；入口存在不等于工具已执行，也不带博客业务接口、数据库连接或秘密。

## 第四章 发现机制与部署关系

### 4.1 机制与本项目选择

官方说明确认仓库级`.agents/skills/`参与本地发现，扫描工作目录至仓库根的相关位置；可以显式选择Skill，也可按description匹配。CLI/IDE有`/skills`或`$`入口；变更未出现时可重启排查。具体桌面入口以实际客户端为准，不保证任意目录中的`skill/`会自动加载。[OpenAI：Build skills](https://learn.chatgpt.com/docs/build-skills)（2026年10月13日核阅）。

本项目采用仓库根目录下普通目录副本，不使用目录联接或符号链接，不写用户级位置。入口与参考都保持包内相对引用，便于从权威目录复制后继续解析。机制说明不是部署执行日志，以下另列项目实证。

### 4.2 已有部署事实

[15.4-A部署记录](../../../skill/docs/软件开发Skill部署记录.md)记载：2026年10月9日约15:31—15:32在Windows、Codex桌面项目环境逐文件复制，15:33:53完成摘要复核。记录中的`codex-cli 0.162.0-alpha.2`只是可访问的CLI程序版本，不是桌面应用发行版本。

当时目标包不存在，检查路径后复制12文件；相对集合、名称、SHA-256和版本一致，包内引用有效，没有覆盖其他Skill。当前本轮只读复核两侧文件集合与摘要，不执行复制或更新；历史完整12项摘要表保留在原部署记录，不在正文重复长散列值。

### 4.3 单向维护原则

维护方向固定为权威源码→指定部署副本。先检查源、目标及未知文件，再同步明确文件，最后比较相对集合、数量、名称、摘要和引用；不得手工分别维护两套规则。出现同名冲突或目标多出未知文件时先报告，不自动清理整个`.agents`目录。

同步、删除过期文件、修改客户端配置及Git发布均需要当次授权。本文描述维护方法，不执行维护动作，也不把上次提交权限继承为当前权限。

## 第五章 格式校验与一致性检查

### 5.1 历史格式校验限制

15.4-A读取并尝试运行内置`quick_validate.py`。系统Python 3.12.0和Codex捆绑Python 3.12.14均未发现`yaml`模块；实际校验命令在导入阶段报`ModuleNotFoundError: No module named 'yaml'`、退出码1，未进入格式判断。

因此状态是环境受限，不是“校验器通过”，也不是“Skill格式被判不合格”。没有为了校验安装全局或项目依赖。本轮仅复用这一历史事实，未重新探测Python、安装PyYAML或运行校验器。

### 5.2 可复核项目与边界

| 项目 | 核查方法 | 能支持的结论 |
| --- | --- | --- |
| 结构 | 列出入口和11份参考，比较两侧相对路径集合 | 文件齐全且无额外副本漂移 |
| 内容 | 对每一对应文件计算SHA-256 | 字节内容一致；不代表业务规则正确 |
| 入口 | 读取name、description、正文版本及路由 | 入口内容存在且可读 |
| 引用 | 逐一解析包内Markdown目标 | 本地目标可定位；不等于客户端已读取 |
| 内置格式 | 在具备依赖且获授权的隔离环境运行校验器 | 仅校验器实际输出可作为其结果 |
| 发现与行为 | 实际清单、入口读取、阶段读取及任务证据 | 分别支持发现、调用和有限流程评价 |

本轮静态复核确认权威12份与部署12份一一对应且摘要一致；未修改两侧文件。内置校验器仍按已有历史记录保留受限状态，不因摘要一致改写结果。

## 第七章 使用步骤与调用示例

### 7.1 使用前检查

1. 在正确项目目录打开Codex任务，确认部署入口和参考文件可读。
2. 通过当前客户端可用清单或选择入口核对名称和路径，避免加载其他同名包。
3. 提供任务对象、依据、允许修改的文件、允许运行的验证及停止点，不在聊天或Skill里写真实凭据。
4. 要求实际读取入口、公共规则和必要阶段；记录版本。若无法发现或读取，应明确说明，不能只按回答风格判断调用成功。
5. 结束时核对成果、证据、未执行项和授权范围；是否进入下一阶段由当前请求决定。

### 7.2 只读诊断示例

以下是未来使用示例，不是新增一次历史执行：

```text
请使用 $software-development-workflow，对指定项目中的某项已记录缺陷做只读诊断。
先读取需求依据、当前源码和已有证据，给出根因、最小方案及编码前测试设计。
本次禁止修改源码、运行真实数据库或执行Git操作；报告后停止。
```

如桌面端不提供`$`选择，也可在请求中明确写出Skill名称，随后核对实际发现及读取轨迹；不要把手工读取任意文件自动等同客户端发现成功。新任务不得未经验证就宣称跨客户端调用一致。

### 7.3 授权修复与文档整理

修复请求应进一步给出确认的方案、允许文件、隔离测试方法和清理边界。Skill先复核G1—G4，再编码、验证和报告。文档请求只选取必要证据并做文档一致性检查，不运行案例脚本。需求确认、代码编辑、数据库、Git和外部发布权限不可相互替代。

## 第八章 更新维护与故障处理

更新时只编辑权威包，核对规则冲突及相对引用，按实际变更维护正文版本，再经授权单向同步并记录摘要。没有实际提交时不预填Git哈希。副本更新后重新核对客户端所读入口和版本；不能因文件复制完成就关闭发现验证。

| 现象 | 最小排查与处理 |
| --- | --- |
| 未发现Skill | 检查工作目录、仓库级部署位置、文件名和元数据；必要时新会话或重启，不任意散布副本 |
| 同名或版本不明 | 核对实际加载路径和摘要，先报告冲突，不覆盖未知资产 |
| 引用不可读 | 检查中文文件名、相对位置及权限；未恢复前不宣称完整规则已加载 |
| 格式校验依赖不足 | 记录失败阶段与未检查内容；补环境须授权，不安装全局依赖 |
| 缺浏览器或隔离库 | 提供可执行计划并标未执行，不改用真实业务数据冒险运行 |
| 结果成功但流程越权 | 按评价标准单独判定流程问题，不能用结果抵消 |

隐式触发稳定性、更新检测、跨操作系统与全部客户端表现仍需另行验证。维护建议不是本轮任务安排。
