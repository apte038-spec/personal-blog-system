## 第一章 引言

### 1.1 编写目的与项目背景

本计划规定个人博客系统后续测试的对象、层次、环境、数据、顺序、判定标准和证据管理方式，为第18份软件测试用例与需求覆盖矩阵提供依据。测试既要检查公开博客、账户和后台管理是否满足需求，也要识别当前实现与正式基线的差异，避免将界面提示成功等同于实际写入成功，或将模拟环境结果等同于完整系统验收。

现有网站先于正式需求基线和软件开发Skill完成基础开发，本文属于回顾性规范化整理，不能解释为网站最初编码前已经建立本计划。15.5和15.6-B两轮修复具有各自的编码前测试设计及实际验证记录，可以复用，但不能据此倒写整个项目的开发、测试历史。

### 1.2 适用范围与术语

计划面向游客、普通用户、管理员使用的已接入页面、53项后端接口及其业务数据。15个末级路由页面、11个Controller和10张业务表是定位测试对象的结构依据，不是用例数或通过数。

| 术语 | 本文含义 |
| --- | --- |
| 需求基线 | 用户批准的目标范围及验收条件，不表示代码已满足或教师已验收 |
| 单元测试 | 受控输入下验证局部方法；Mockito替身不执行真实数据库或SMTP |
| 前端隔离测试 | 执行实际前端逻辑并以替身响应请求；不证明真实JWT或数据库行为 |
| 模拟HTTP浏览器检查 | 实际浏览器操作真实Vue页面，但HTTP业务响应来自本地夹具 |
| 集成/系统测试 | 真实前端、后端、安全链及独立数据库在明确边界内协同验证 |
| Unicode码点 | 密码、用户名及配置目标规则的计数单位；不同于UTF-16字符串长度及视觉字符数 |
| 证据状态 | 源码存在、历史执行、历史通过、本轮重新通过、未执行分别记录，不互相替代 |

## 第二章 测试目标与依据

### 2.1 总体目标

测试应形成“需求—场景—输入—预期—实际观察—缺陷—回归—证据”的追踪链，验证业务闭环、角色隔离、异常反馈和数据一致性。测试目标包括正常业务可完成，非法输入与无权限操作被正确拒绝，写入失败不报告成功，已批准规则在前端、后端与数据库层得到一致落实。

| 需求集合 | 数量 | 覆盖目标 |
| --- | ---: | --- |
| BLOG-F-001—BLOG-F-040 | 40 | 每项建立正常、适用异常及角色场景；涉及持久化时核对实际数据 |
| BLOG-NF-001—BLOG-NF-011、BLOG-NF-013—BLOG-NF-016 | 15 | 明确方法、环境、可测指标和证据；不能只以功能演示代替 |
| BLOG-BR-001—BLOG-BR-024 | 24 | 对状态转换、唯一性、身份比较、关联和事务建立正反例 |
| BLOG-NF-012 | 1 | 保留追踪行，标为后续窄屏专项候选，不计本期必须验收 |
| 合计 | 80 | 本期79项纳入测试规划；规划覆盖不等于实现覆盖或执行通过 |

### 2.2 测试判据来源

正式SRS规定预期行为，源码用于识别实现和风险，既有报告用于证明历史执行。三者不一致时记录差异，不能为了使当前代码通过而降低验收目标。测试中发现目标含义不清，先提交用户澄清；涉及业务范围改变时按需求变更流程处理，不在测试记录中擅自批准。

已批准的密码码点/字节边界、配置五键、旧Token失效、永久去重、性能和最小竞争参数继续有效。技术实现方法、实际环境版本、历史数据兼容情况及执行证据仍需后续取得。

## 第六章 测试数据设计

### 6.1 数据类别与隔离原则

| 数据类别 | 拟准备的数据 | 关键用途与限制 |
| --- | --- | --- |
| 账号 | 专用USER、ADMIN、DISABLED账号；角色变化对象；正常、边界、重复身份 | 测试用户名49/50/51码点、邮箱trim/大小写和冲突；不用真实个人账号及演示管理员改密 |
| 密码与JWT | 临时测试密码、不同码点/字节组合、受控旧哈希、同账号多个Token | 不在报告留完整密码/Token；旧哈希夹具不等于已知真实旧账号密码，不能从哈希推断原字节数 |
| 文章 | 草稿、发布、置顶、已逻辑删除、同排序指标、不同分类标签的文章 | 测试可见性、时间、计数和确定性顺序；独立于已有正文文章 |
| 分类标签 | 启用、停用、未引用、被有效草稿/发布文章引用、历史停用关联 | 分清新增关联与原关联保留；不自动删除历史关系 |
| 互动 | 同/不同用户及文章的点赞；PENDING/APPROVED/REJECTED评论留言；相同内容 | 检查永久唯一组合、状态转换、审核数与公开范围；不以改变时间或审核状态释放去重 |

### 8.3 最小竞争、邮件及文件专项

并发一致性与性能分开：按BLOG-NF-007/Q10，对当前范围的点赞/取消、评论审核、同邮箱验证码发送分别安排每场景2并发请求、重复10轮。每轮从可核对初态开始，记录请求结果、提交顺序可见信息和最终状态，不把2请求小规模竞争称为高并发认证。

| 场景族 | 预期不变量与注意事项 |
| --- | --- |
| 同用户同文点赞、取消及适用竞争组合 | 关系最多1条，幂等不重复增加；最终like_count与有效关系一致且非负；按具体组合确定最终合法状态，不预设竞态请求顺序 |

| 同邮箱发码竞争 | 60秒限制不被绕过，同一轮最多一个发码业务成功，只有合法最新未用码有效；新码使旧码失效，错误分支不得伪装成功 |

发码多轮须合理安排不同专用邮箱/受控时间或经批准重置独立夹具，避免上一轮60秒窗口污染下一轮。先使用受控邮件替身验证竞争，真实SMTP另测，不发送大量真实邮件。真实收件按基线从发送请求起观察120秒，记录脱敏发送/收到时间并完成有效码重置及新密码登录；未收到记该次未通过或环境受限，不承诺SMTP送达保证。邮件已发但库失败时不能假定邮件可回滚，仍按库内有效码及失败反馈判断。

头像专项同时验证数据库提交/回滚与新旧文件补偿；预览取消不发上传，真实上传后个人中心和导航同步。仅验证文件头不等于完整图像解码或恶意文件全检，具体证据必须说明已测到的层次。

## 第十一章 准入、通过与退出标准

### 11.1 准入标准

执行前应确定被测源码和SRS版本、详细用例及预期、依赖/工具可用性、测试库和文件隔离、脱敏记录方式、回收/停止方法及真实执行授权。存在已知实现缺口时可进入受控诊断测试，但须标注预期失败风险，不能伪装为验收就绪。

涉及生产数据或真实SMTP无授权、目标库不明确、服务代理可能回落真实业务端、关键环境无法复现时，不准启动相应测试；改记未执行/环境受限并报告所缺条件。

### 11.2 单项结果判定

| 状态 | 判定 |
| --- | --- |
| 通过 | 实际执行，所有适用预期均满足，证据能定位；需核对数据的用例不能仅凭200或弹窗判过 |
| 失败 | 已执行且与需求/预期不符；HTTP200但Result失败、写入未生效、错误回滚或误报成功均按实际处理 |
| 未执行 | 尚未运行、只设计、范围未授权或缺少前置数据；没有执行结果不记通过 |
| 环境受限 | 已明确尝试或核验后受工具、权限、服务等阻断；记录限制与影响，不改称业务通过 |

测试脚本的预期拒绝场景可“用例通过”，即业务返回正确错误；不能把全部非200一律算系统故障。更新0行要结合对象不存在、实际写入失败和幂等无变更区分，不能机械用影响行数一个条件替代业务判定。

### 11.3 严重程度与回归标准

建议缺陷分级用于安排修复，不改变需求优先级：致命为越权、凭据泄露、测试误入真实数据环境或严重数据破坏；严重为核心业务无法完成、Token永久失效/事务等安全一致性目标失效；一般为局部交互、边界或明确反馈不符；轻微为不阻断业务的文字/布局问题。具体分级结合影响由用户复核，不能仅因界面仍可操作降低安全缺陷等级。

修复前保留复现、根因和预期；授权修复后执行原失败场景、同类分支及相邻功能，记录旧/新版本。代码修改成功但未验证只能待验证，仍失败保持未关闭，环境受限不得自动关闭。历史失败记录保留，回归通过另记真实结果。

### 11.4 退出与验收建议

建议退出评审的条件是：79项本期需求均有可追踪的执行结果或明确未执行原因；全部Must满足并有适用证据，严重安全/数据缺陷未关闭时不建议验收；Should未满足或未测需逐项公开并由用户决定后续安排，不能擅自豁免。批准性能、桌面兼容、SMTP及独立数据库专项需各自结果，不能用单元通过替代。

未具备上述条件时可以阶段性结束测试并交付局限报告，但结论应为“阶段验证完成、存在待验收项”，不是完整验收通过。教师/学校验收需真实另行发生，本计划不预填。

### 12.1 现有差异的验证安排
