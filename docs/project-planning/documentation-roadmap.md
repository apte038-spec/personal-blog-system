## 3. 需求可追踪与测试前置规则

Skill和后续正式文档都应维护以下链路：

```text
需求来源 → 需求编号与验收条件 → 原型/设计元素 → 前端/后端/数据库实现 → 测试用例 → 执行结果/缺陷 → Git提交
```

最低追踪字段建议包括：需求ID、来源、描述、优先级、确认状态、验收条件、相关页面/接口/表、测试用例ID、当前实现状态和对应提交。未知项必须标记为待确认，不允许由AI自行补成确定需求。

测试顺序应遵循课堂要求：

1. 需求形成后，将需求改写为可验证的验收条件。
2. 在系统详细设计和编码前完成测试计划、测试场景、测试用例及预期结果初稿。
3. 使用原型对需求和主要测试场景进行早期验证。
4. 设计完成时复核测试覆盖范围；实现期间补充单元/集成测试；执行后记录真实结果和缺陷。
5. 测试报告只记录实际运行证据，未测项目标为“未执行”。

## 4. Codex Skill 的格式、发现和调用规划

### 4.1 当前环境能确认的格式

当前 Codex 安装的 Skill Creator 规范确认：一个 Skill 是一个含必需`SKILL.md`的目录，入口文件使用YAML frontmatter，至少声明`name`和`description`；可按需使用`references/`、`scripts/`、`assets/`和`agents/openai.yaml`。描述决定何时考虑该Skill，主体提供核心流程，详细的阶段规则放到按需读取的参考文件中。创建后可运行对应的`quick_validate.py`检查frontmatter、命名和脚手架占位内容；格式通过不等于行为有效，仍需真实任务验证。

本机当前可用Skill清单没有发现本项目的全流程Skill；仓库中的`skill/README.md`只是目录说明。**把文件放在仓库的`skill/`目录不等于Codex自动发现或自动调用。**2026-10-08核对[OpenAI官方Build skills说明](https://learn.chatgpt.com/docs/build-skills)，当前文档列出仓库级`.agents/skills`和用户级`~/.agents/skills`等发现位置；本机还存在`.codex/skills`中的系统技能，不能据此假定所有环境具有同样路径。计划保留`skill/`中的可维护源文件，创建时再按实际客户端支持的发现位置部署并验证。官方说明CLI/IDE可通过`/skills`或`$`选择技能；桌面端届时按实际技能选择器和可见清单确认，不把单一调用方式当作通用保证。本轮不安装、不开发Skill。

### 4.2 Skill入口职责

入口文件应简洁说明：适用于需要跨越需求、原型、设计、实现、测试和交付的软件项目；根据用户当前阶段决定工作，不强迫每个小任务从头执行。入口负责：

- 判断用户目标、项目状态、当前阶段和授权边界；
- 读取现有代码、配置、SQL、测试、文档和Git差异，优先引用实际证据；
- 对每阶段定义输入、输出和退出条件；
- 不确定需求、重大设计选择和超出授权的外部操作先整理选项并请求确认；
- 保持需求到设计、实现和测试的追踪；
- 记录真实变更及验证，不伪造会议、原型评审、测试结果或Git历史；
- 阶段完成后提供清单和证据，等用户确认再进入下一阶段。

### 4.4 用户确认机制和需求变更

- 用户明确要求单一小节/阶段时，Skill只完成该范围，完成后停止。
- 新需求可能改变接口契约、数据库结构、权限、兼容性或交付范围时，先提交影响分析和选择项等待确认。
- 变更记录包括提出者/来源、日期、变更前后、原因、影响的需求/页面/接口/表/测试及批准状态。
- 对在范围内的只读检查、可逆且明确授权的本地工作，可自主推进；GitHub推送、覆盖历史、删除数据等动作另行确认。

### 4.5 本项目验证方法

1. **回顾性审查**：让Skill读取博客系统现有路由、Controller/Service/Mapper、SQL、测试和文档，输出需求—页面—接口—数据—测试的差距；标为回顾审查，不声称历史上由Skill产出。
2. **前瞻性试用**：从之后真实发生的需求补充或缺陷修复中选一项，按Skill工作流形成需求记录、影响分析、实现、测试证据和正常Git提交。
3. **检查指标**：来源是否清晰、待确认项是否保留、需求追踪是否完整、测试是否早于实现计划、测试结果是否真实、改动是否符合授权、阶段门是否等待确认。
