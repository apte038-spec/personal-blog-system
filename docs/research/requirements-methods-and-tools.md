## 摘要

需求工程的工作不只是把功能写成清单，而是从业务目标和相关人员的实际任务中发现问题，分析需求之间的关系，再把已确认的需求转换为可以设计、实现和验证的表达。本报告结合老师课堂要求和当前个人博客系统代码，研究常用需求获取、分析、表达方法及其工具，比较结构化文字、用户故事、用例、流程图、原型和数据模型的适用范围，并提出适合本项目的组合方案。

报告中的项目功能描述来自当前 README、Vue 路由和 API 封装、Spring Boot Controller/Security 配置以及数据库初始化脚本。它们是对**已实现系统的现状归纳**，不等同于早期需求会议记录，也不能据此声称项目开发前已经完成过访谈、问卷或原型评审。

## 1. 研究背景与目的

软件开发中的需求决定系统要解决的问题、服务对象、业务范围和验收标准。如果需求含糊、遗漏或互相冲突，后续页面、接口和数据库即使能够运行，也可能没有解决使用者的真实问题。老师在课堂转写中强调，业务应用的软件需求应从业务目标、参与者、业务流程、业务模块、信息与业务规则出发；还要求研究需求获取与表达、需求会议和需求变化管理，并提醒在需求与设计阶段准备测试计划、测试用例和预期结果。以上是本课程明确的研究方向；具体方法、文档模板和工具选择由本报告研究后提出，不冒充老师指定内容。

在 AI 辅助开发中，编码和生成文档的速度提高，但这并不能自动证明需求正确。AI依据收到的上下文生成建议，输入材料不完整时，输出也可能遗漏业务约束、把假设写成事实，或生成与现有代码不一致的功能。AI适合协助整理、比较、追踪和审查，不能代替用户说明真实目标、责任人确认业务规则，也不能代替人工判断验收是否符合预期。需求工程因此仍然重要：它为AI提供边界清楚的输入，并为设计、实现和测试提供可追溯依据。

ISO/IEC/IEEE 29148规定了系统与软件生命周期中的需求工程过程和需求相关信息项，可作为需求过程和规格说明的参考框架；NASA系统工程手册提供了需求表述、确认、正确性、可验证性和追踪性的检查清单。本报告采用这些公开指导作为质量参考，不宣称课程项目必须满足特定行业认证。[ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html)；[NASA Systems Engineering Handbook](https://www.nasa.gov/wp-content/uploads/2018/09/nasa_systems_engineering_handbook_0.pdf)

本报告的目的如下：

1. 对常见需求获取方法的工作方式、适用条件和局限进行比较；
2. 建立从业务理解到需求分析和需求表达的基本步骤；
3. 比较PC Web项目可用的文本、图形和原型工具，区分方法、表示法与软件工具；
4. 基于博客系统实际功能提出后续需求规格说明书、原型和测试材料的推荐做法；
5. 为后续全流程 Skill 规定需求来源、确认状态、追踪关系和人工确认的基本质量要求。

## 2. 需求获取方法

需求获取是从利益相关者、现行业务、既有系统和外部约束中收集需求证据的活动。方法应按问题和对象组合使用，不存在适用于所有项目的单一最佳方法。IREB的需求工程课程材料将需求获取、文档化、验证与管理视为相互关联的活动，并指出不同工作产品和方法存在适用性差异。[IREB CPRE Foundation Level](https://cpre.ireb.org/en/concept/foundationlevel)

| 方法 | 基本原理 | 适用场景 | 局限与风险 | 个人博客系统中的适用性 |
| --- | --- | --- | --- | --- |
| 访谈法 | 与用户、管理员或业务负责人一对一或小范围提问，围绕目标、任务、困难、异常和优先级追问，并记录事实、观点和待确认项。可用半结构化提纲保持主题一致，同时根据回答追问。 | 角色较少、业务细节需要解释、需要了解动机或规则的项目；例如了解管理员如何发布和审核内容。 | 结果受受访者记忆、表达、问题引导和访谈者理解影响；只访谈一人可能忽略其他角色。事后摘要必须由参与者确认，不能把推测写成原话。 | 适合后续向博客所有者/管理员了解文章发布、分类标签维护、评论留言审核及站点配置目标；面向普通用户可询问浏览、点赞、评论和个人中心体验。当前没有已归档的访谈记录。 |
| 问卷调查法 | 使用一组统一问题收集较多对象的选择、评价或开放意见；适合统计偏好或验证已有假设。 | 用户群体较大、问题边界已明确、需要对同一主题获得可比较反馈时。 | 问题措辞、选项设置和样本来源会造成偏差；低回应率、误解题意和无背景的答案会降低可信度；问卷不擅长揭示复杂业务流程与深层原因。 | 只有在需要收集多个博客读者对阅读体验、分类入口或页面易用性的意见时才值得使用。当前没有问卷数据，不应报告任何统计结论。 |
| 观察法 | 观察目标用户在真实或模拟环境中完成任务，记录实际操作、等待、错误、绕行步骤和上下文，而不只依赖其口头描述。 | 任务流程明显、用户难以准确描述操作、现有系统或纸面流程可观察时。 | 观察者可能影响行为；短时间样本不一定代表常态；需要保护个人信息，且不能仅靠观察推断用户动机。 | 可观察普通用户从首页查找文章、筛选文章、阅读详情并发表评论的操作，也可观察管理员审核评论/留言的任务。若只检查当前浏览器页面，应称为可用性检查，不声称已做真实用户观察。 |
| 文档分析法 | 检查现有政策、业务表格、流程说明、旧系统、代码、数据库、接口和运行日志，从中识别术语、现行规则、数据来源、约束和功能。 | 项目已有系统、代码、数据库、制度文件或迁移材料；需求变更、旧系统改造和课程项目回顾尤其适合。 | 文档可能过期、互相矛盾或只记录实现而未记录真实需求；代码只能证明当前实现存在，不能证明用户认可该实现。 | 对当前项目最直接可用：本次已检查README、路由、API封装、Controller/Security、`schema.sql`和用例图。结论应标为“代码/配置/SQL现状”，再通过用户确认转成需求基线。 |
| 头脑风暴/需求工作坊 | 多名参与者围绕明确问题共同提出目标、场景和方案，先扩展思路，再归类、澄清、评估和决策；主持人负责聚焦议题和记录分歧。 | 需求空间尚未完全明确、需要协同多个角色、需要快速发现备选方案或达成共同理解时。 | 容易受强势发言者、群体从众和讨论跑题影响；提出的点子不自动成为需求，必须筛选、补充依据并确认。 | 适合围绕博客站点定位、前台内容发现、互动审核策略或管理员工作台做短时工作坊。当前未提供真实会议材料，因此不能补写会议结论。 |
| 原型法 | 用低保真线框图、可点击原型或局部交互模型呈现页面与流程，让使用者针对可见对象反馈；通过迭代减少抽象文字造成的误解。 | 页面流程和交互较多、需求难以仅靠文字确认、表单/导航/状态变化需要早期验证的PC Web应用。 | 用户可能把原型误认为成品、过度关注配色而忽略业务；原型若过早固化，会限制替代方案；原型本身也不证明接口、安全、性能已实现。 | 适合登录注册、文章筛选与详情、发表评论/待审核提示、个人中心和后台批量审核流程。仓库`prototype/`当前只有目录说明，尚无正式原型文件或评审记录。 |

### 2.1 方法组合建议

对本项目及后续博客功能变更，建议按以下顺序选择方法：

1. **先做文档和现状分析**：查看课程要求、用户说明、README、路由、API、Controller、Service、实体、SQL和测试，标出“已实现”“未实现”“未知”。
2. **再做角色访谈或书面确认**：分别确认博客所有者/管理员、普通用户和游客的目标与约束。角色少时，短访谈比大规模问卷更有效；若没有真实受访者，应将来源标成“项目负责人提供的需求说明”，不伪装成访谈。
3. **对流程性问题使用观察或场景走查**：让参与者实际完成任务，记录步骤、异常和结果；没有参与者时可做代码/页面走查，但标注为桌面分析。
4. **需要多个角色共同决策时组织小型工作坊**：限定问题、形成备选项、逐项记录决策及待确认事项。
5. **对页面交互用原型澄清**：先低保真，确认流程后再决定是否补充视觉稿或可点击原型。
6. **将所有结果落到需求清单并回访确认**：每条需求保留来源、角色、优先级、验收条件、状态和变更记录。

## 3. 需求分析方法

需求分析把收集到的材料转化为结构清楚、相互一致且可验证的需求。分析时应先理解业务目标和业务流程，再确定系统边界、用户角色、功能、数据、状态、约束和验收条件。老师课堂也特别强调业务目标、参与者、业务模块、信息流和业务规则应在系统功能设计前被梳理。

### 3.1 功能需求

功能需求说明系统在特定条件下应提供的行为或服务。每条需求应描述执行者、触发条件、输入、处理结果和失败/异常行为，避免仅写“支持用户管理”这种不可直接验证的功能名称。

**示例（根据现有代码整理的现状，不是早期需求会议原文）：**访客可按关键词、分类或标签查询已发布文章，列表支持分页。对应代码证据包括前端`ArticleList.vue`、`publicApi.articles`和后端`PublicArticleController`公开文章分页接口。此表述仍需在正式需求基线中由项目负责人确认。

### 3.2 非功能需求

非功能需求描述系统质量、约束或运行条件，例如安全、可用性、响应性能、兼容性、可维护性和可恢复性。应尽量定量并指定验证方式；“系统要安全”“页面要快速”不足以构成可测需求。

对个人博客系统可进一步确认的主题包括：管理员接口的授权边界、密码保护、头像格式与大小限制、页面在常见屏幕下的可用性、分页规模、错误提示和备份恢复方式。除代码/配置中已有的约束外，未核实的数值目标不得自行写为当前系统承诺。

### 3.3 业务规则

业务规则定义业务允许、禁止、先后顺序或状态变化，例如文章发布状态、分类是否可删除、评论审核后是否公开、账号禁用后的访问限制。规则应独立记录，再映射到页面提示、后端校验和数据库约束，避免只在页面文字中出现。

当前代码可观察到的例子包括：公开文章查询只返回已发布文章；评论和留言提交为待审核，公开查询只显示审核通过内容；普通用户和管理员角色有不同的后台权限。以上是对现状实现的归纳；具体边界仍以当前后端实现为准，并应在后续SRS逐条核实。

### 3.4 用户角色与目标

角色是具有相似目标、权限和使用场景的用户类别。当前项目至少有：

- **游客**：浏览公开文章、关于我和已审核留言，注册、登录和重置密码；
- **普通用户（USER）**：在公开浏览基础上点赞、评论、留言、使用个人中心、上传头像、修改个人信息和密码、查看喜欢的文章；
- **管理员（ADMIN）**：在普通用户功能基础上管理文章、用户、评论、留言、分类、标签和站点配置，并查看统计。

角色名称和权限由当前README、Vue路由守卫、Spring Security与后台接口共同支持。对未登录请求和后台权限，应同时检查前端体验与后端最终授权，不能只依赖隐藏菜单。

### 3.5 需求优先级

课程项目可采用MoSCoW或“高/中/低+理由”的轻量优先级法：

- **Must（必须）**：完成项目核心业务和验收闭环所不可缺少；
- **Should（应该）**：重要但可在核心流程稳定后完成；
- **Could（可以）**：有时间时实现的改进；
- **Won’t for now（暂不做）**：明确本期不纳入的事项。

优先级应由项目负责人/相关使用者确认，不能由分析者或AI根据技术喜好单方面决定。评论附件上传、复杂通知或多层权限等当前未实现内容，不应被写成既有功能；本项目已有本地头像上传，不能将其与评论附件混淆。若将来提出新能力，应先登记为新需求并评估范围。

### 3.6 需求冲突分析

需求冲突常见于不同角色的目标不一致、旧规则与新规则不一致、性能与安全约束之间的取舍，或两个表述要求相反行为。建议处理步骤：

1. 标出冲突需求的编号、来源、提出角色和证据；
2. 复述各方真正要解决的问题，区分目标与解决方案；
3. 核对法律/课程要求、业务规则、系统边界和技术限制；
4. 形成至少两个可比较方案，说明对页面、接口、数据、权限和测试的影响；
5. 由有权确认的人选择，记录理由、时间和需求版本；
6. 更新受影响的设计、原型、测试和实现追踪关系。

没有明确决策人或证据时，将需求标为“待确认”，不得让AI自行裁决。

## 4. 需求表达方式

方法/表示法回答“用什么形式描述需求”；软件工具回答“用什么工具编写、绘制、协作或保存”。一个工具可支持多种表示法，一种表示法也可由多个工具实现。

### 4.1 自然语言需求

自然语言便于用户和学生阅读，适合说明目标、上下文和业务约束。其主要风险是代词不清、范围词不明、一个句子包含多项行为，以及“方便、快速、友好”等无法验收的形容词。可使用“系统应……”陈述，并在单条需求中只保留一个主要义务。

### 4.2 结构化需求条目

建议每条需求至少包含：

| 字段 | 用途 |
| --- | --- |
| 需求ID | 提供稳定引用，如`BLOG-F-001` |
| 来源 | 用户说明、课堂任务、现行代码/SQL或其他证据 |
| 角色/目标 | 标明谁需要什么结果 |
| 需求陈述 | 用清晰、单一、可验证的句子表达 |
| 优先级与状态 | 记录优先级、草拟/待确认/已确认/已实现/已验证等状态 |
| 验收条件 | 描述通过标准及必要的异常场景 |
| 关联项 | 对应页面、接口、数据、测试用例和变更版本 |

结构化模板提升一致性，但字段多不等于需求质量高；必须避免为了填表而虚构来源或验收指标。

### 4.3 用户故事与验收条件

用户故事可采用“作为[角色]，我希望[目标]，以便[价值]”的简短格式，适合敏捷讨论和表达用户目标。它不应替代详细业务规则、权限要求或复杂流程。应为重要故事补充验收条件，例如给出前置条件、操作和可观察结果；条件可用示例/场景描述，或采用Given-When-Then格式。

**示例（按现有实现整理的示例，待纳入需求基线前确认）：**作为已登录用户，我希望对文章发表评论，以便参与交流；提交后评论处于待审核状态，审核通过后才出现在文章评论区。此示例反映现有功能，不声称是实际用户访谈原句。

### 4.4 用例描述与用例图

用例描述关注参与者为达成目标与系统进行的交互，可包含前置条件、触发器、基本流程、备选/异常流程、后置条件和业务规则。用例图在较高层次展示参与者与系统功能之间的关系，适合说明范围和角色；它本身不描述完整交互细节。

当前仓库已有`docs/design/use-case/系统用例图.puml`及PNG、SVG，可作为现状图示材料。正式需求分析仍需检查图中的角色、用例和权限是否与当前代码一致，并为重要用例增加文字描述。该图存在不等同于已完成全部需求规格说明。

### 4.5 业务流程图、活动图与状态图

- **业务流程图/BPMN**：描述参与者、业务活动、分支、交接和结束条件，适合跨角色讨论工作如何完成。OMG的BPMN规范强调其作为业务人员、实施者和管理人员之间的流程沟通表示法。[OMG BPMN 2.0](https://www.omg.org/spec/BPMN/2.0/About-BPMN)
- **UML活动图**：描述一组动作、条件分支和并行/顺序控制，适合表达系统内某个用例的处理流程。过度追求形式完整会让简单功能难以阅读。
- **状态图**：描述对象状态及触发状态转换的事件/条件，适合存在明确生命周期的对象。例如文章草稿与发布状态、评论待审核/通过/拒绝、账号启用/禁用。状态与转换必须以实际业务规则为准。

### 4.6 数据模型与页面原型

- **数据模型/ER图**用于说明核心实体、属性和关系，支持发现信息遗漏和关联规则；它是需求和设计之间的模型，不是用户功能清单，也不自动等于最终SQL。
- **页面原型**用于展示页面结构、信息层次、导航和关键交互；适合验证用户是否能理解筛选、审核、资料修改等操作。原型应带需求编号或目标说明，以免图形与需求脱节。
- **测试场景/验收表**用于把需求转化为可观察的结果。需求、设计和代码应共同为测试提供输入，而不能只根据最终写出的代码反推“本来就是需求”。

### 5.1 方法与软件工具的区别

“访谈”“问卷”“观察”“文档分析”“工作坊”“原型评审”是获取或验证需求的方法；“用户故事”“用例”“BPMN流程”“状态图”“ER图”是需求/业务的表达形式或建模表示法；Markdown、PlantUML、Mermaid、draw.io、Figma和Axure是编写、绘制或展示这些材料的软件工具或文本工具链。工具不会自动保证需求正确，画出用例图也不等于已经完成需求分析。

## 6. 需求质量要求与检查方式

ISO/IEC/IEEE 29148及NASA手册可用于建立需求质量检查基准。NASA手册的检查清单特别关注需求是否必要、正确、唯一可引用、术语一致、可验证以及双向追踪。[NASA需求编写检查清单](https://www.nasa.gov/wp-content/uploads/2018/09/nasa_systems_engineering_handbook_0.pdf)

| 质量属性 | 含义 | 检查问题/方法 |
| --- | --- | --- |
| 正确性 | 需求反映确认过的用户目标、业务规则和系统边界。 | 是否有明确来源？目标角色是否确认？是否把当前实现错误地当成用户需求？ |
| 完整性 | 对范围内的正常流程、重要异常、数据和质量约束没有关键遗漏。 | 是否覆盖各角色和关键状态？是否考虑失败、空数据、未授权及边界情况？未覆盖处是否标为待确认？ |
| 一致性 | 需求之间不相互矛盾，术语、角色、状态和规则用法一致。 | “游客/用户/管理员”“待审核/已通过”等词是否统一？新旧规则是否冲突？ |
| 无歧义性 | 不同读者能得出相同理解。 | 是否避免“尽快、很多、友好”等不确定词？是否明确对象、条件、数量、权限和结果？ |
| 可验证性 | 需求有可观察的验收方式和判定条件。 | 能否设计检查、测试、演示或文档审查来判定满足与否？结果是否可重复？ |
| 可追踪性 | 需求可追到来源、设计/实现和测试，相关变更可双向定位。 | 是否有稳定ID、来源、页面/接口/表/测试关联？删除/变更需求时能否查出影响？ |
| 可修改性 | 需求结构清楚，变更一项时能识别影响并控制重复信息。 | 是否按功能/角色/主题拆分？同一规则是否只维护一个权威位置？版本和变更理由是否记录？ |

建议每次需求评审采用检查表：逐项确认来源、角色、术语、唯一性、边界、状态转换、异常流程、验收条件和追踪关系。若无法确认，记录待确认问题与责任人，不通过润色掩盖缺口。

## 7. AI辅助需求工程：Codex 的作用与局限

### 7.1 可承担的辅助工作

在提供相应项目文件和清晰任务边界后，Codex可协助：

- 检索README、路由、API封装、Controller、Service、Mapper、Entity、SQL与测试，形成“当前实现事实”清单；
- 把用户描述整理为角色、目标、场景、规则和待确认问题；
- 生成访谈提纲、问卷草案、需求条目、用户故事、用例和流程图草稿；
- 比较需求之间的重复、冲突、缺少的异常场景和不可测试表达；
- 建立需求到页面、接口、数据表和测试用例的初步追踪矩阵；
- 对照代码和文档，识别“文档承诺但代码未实现”或“代码已存在但需求文档未覆盖”的差异。

Codex Skill可由`SKILL.md`和必要的参考文件/脚本组成，用于给模型提供可复用流程和约束；它提供的是工作流程指引，不是自动验证业务正确性的权威系统。[OpenAI Skills文档](https://developers.openai.com/plugins/concepts/skills)

### 7.2 主要局限

1. **不能替代真实需求来源**：AI无法仅从代码推断用户真正想要什么；代码只能反映现状。
2. **可能补全未说明内容**：模型可能把常见产品设计当成项目事实。所有推断、假设和待确认项应显式标识。
3. **无法自行代表利益相关者确认**：需求基线、冲突裁决、优先级和范围取舍必须由有权人员确认。
4. **代码证据有边界**：静态代码中出现某个接口不代表功能在运行环境已通过端到端验证；测试结果要实际执行。
5. **工具输出也要审查**：图表可能语法正确但业务关系错误；自然语言生成也可能遗漏权限和异常场景。
6. **资料安全和授权受限**：向AI提供数据时，应遵守课程、组织和隐私要求，不上传真实密码、令牌、用户敏感信息或未授权材料。

因此，合适的协作方式是“AI提出与整理，人确认目标和规则，代码/测试提供实现证据”：AI可以草拟，不能擅自确认；AI可以发现可能冲突，不能替相关角色作业务裁决。

## 8. 个人博客系统的适用性分析

### 8.1 项目事实与证据范围

当前系统为Vue 3 + Spring Boot + MySQL的PC Web前后端分离项目。有效路由包含首页、文章列表、文章详情、关于我、留言板、个人中心、登录/注册、忘记密码、404及后台数据概览、文章管理、用户管理、评论管理、留言管理和系统管理。系统管理页面内部包含分类、标签和站点配置页签。

当前实现的核心业务包括：

- 公开文章分页、关键词/分类/标签筛选、最新/热门/置顶文章和相邻文章；

仓库已有系统用例图以及数据库脚本中10张表。上述内容可从README、`blog-web/src/router/index.js`、`blog-web/src/api/`、后端Controller/Security及`schema.sql`核验。它们构成“现状分析”证据，不表示已知每项功能的历史需求来源。

### 8.3 本项目推荐的需求获取组合

考虑当前系统已开发完成，建议分两类开展：

**对现有系统做回顾性基线整理：**

1. 先以README、Vue路由与API、Controller/Service、数据库SQL和自动化测试做文档分析；
2. 将直接代码证据标为“现状实现”，推断内容标为“待确认”；
3. 与项目负责人逐项确认哪些现有行为应作为本课程系统需求，哪些属于实现选择或历史遗留；
4. 选取注册登录、文章浏览、评论审核、头像上传和后台文章管理等核心流程做桌面走查；
5. 仅在出现用户目标或优先级争议时组织访谈/短工作坊，不为满足文档数量而制造访谈或问卷。

**对后续新需求或缺陷修复：**

1. 记录提出来源和业务目标；
2. 对简单变更使用结构化问题确认；对角色/流程复杂的需求进行访谈或小型工作坊；
3. 页面交互变化先制作低保真原型并确认；
4. 形成编号需求、验收条件和测试用例初稿；
5. 经确认后再更新设计和代码。

### 8.4 示例需求的证据标注方式

为避免把研究示例误写成历史事实，正式文档建议采用以下标签：

- **代码事实**：由当前文件、接口、SQL或测试直接支持；
- **用户/老师确认**：由可追溯的实际说明、会议确认或书面材料支持；
- **分析推断**：依据现有事实提出，尚未确认；
- **建议需求**：用于讨论的方案，不代表当前系统能力；
- **待确认**：关键来源或规则尚不明确。

例如：“评论提交后为待审核状态”可标为代码事实；“用户希望收到审核结果通知”若代码和材料均无证据，则只能标为建议需求或待确认，不能写成已实现功能。

## 9. 研究结论与推荐方案

需求获取与表达应采用多种方法组合：以现有文件、代码和数据库分析建立事实底稿，以访谈或书面确认补足用户目标与业务规则，以观察/走查发现流程差异，以原型验证页面和交互，再用结构化需求、用例、流程图和验收条件形成可追踪的表达。优先级、需求冲突和变更须有明确决策来源。

针对当前个人博客系统，后续建议采用以下组合：

1. **需求主文档使用Markdown**，每条需求提供稳定ID、来源、角色、描述、优先级、确认状态、验收条件及关联设计/测试；
2. **用例描述与用例图并用**：保留现有PlantUML用例图源文件，核对后补充关键用例文字说明；
3. **流程和状态采用简洁图形表达**：在Markdown中优先使用Mermaid描述轻量流程；需要严格UML控制或稳定导出时使用PlantUML；跨角色业务流程可按需使用BPMN/draw.io；
4. **原型采用低保真起步**：先用Figma或draw.io表达页面布局和主要跳转，只有交互状态确有必要时再做可点击/高保真原型；Axure RP作为复杂交互备选，不作为必须工具；
5. **测试提前准备**：在系统设计和编码前根据确认需求形成测试场景、测试用例和预期结果，原型阶段先验证关键流程，之后依据实现补充自动化和回归测试；
6. **全过程保持人工确认**：Codex可分析和草拟，但不能替用户确定业务目标、需求优先级、冲突处理结论、原型确认或测试通过；
7. **对已完成系统如实标注来源**：本次整理是代码现状分析与回顾性需求确认，不补写不存在的访谈、问卷、需求会议或原型评审。
