# 软件开发Skill阶段规则与质量门

## 1. 使用约定

本文件定稿的是供15.3编写使用的执行规则方案，仍待用户检查，不是已部署Skill。阶段可裁剪，但真实性、授权和必要验证不能通过裁剪消失。整体任务映射见[总体设计](软件开发Skill总体设计.md)，文件职责见[目录设计](软件开发Skill目录与引用设计.md)。

阶段状态使用：未开始、进行中、满足、条件满足、阻塞、不适用、用户暂缓。未执行或环境受限必须另行写明，不能归为通过。“条件满足”应列出限制、补偿措施与后续责任，不能用于隐去核心验收缺失。

## 2. 九阶段规则

### S1 项目启动与需求理解

| 要素 | 规则 |
| --- | --- |
| 触发与输入 | 所有任务启动；输入用户请求、项目目录、现有指令、可用资料和授权边界 |
| 步骤 | 检查项目指令与资产；识别任务类型、真实状态、基线、限制和阶段停止点；制定裁剪路径 |
| 输出 | 范围摘要、证据清单、信息缺口和阶段计划 |
| 质量检查 | 现有与计划分开；确认工作区已有修改归属；不泄露秘密 |
| 用户确认 | 目标有多种实质不同解释、需扩大范围或写入权限不足时询问 |
| 下一阶段 | 范围足以支持下一项工作；只读任务可直接进入对应分析并报告 |
| 信息不足 | 先做安全只读核查；不能核实的事实标为未知，关键缺口交用户决定 |
| 允许跳过 | 不可完全跳过；同一任务续作可复用已核实上下文并检查变化 |
| 风险记录 | 标注复用的材料、未重新核查的范围及可能过时之处 |

### S2 需求分析与变更管理

| 要素 | 规则 |
| --- | --- |
| 触发与输入 | 新功能、规则冲突、正式确认或变更；输入基线、需求清单、用户决定和实现证据 |
| 步骤 | 区分现状与目标；整理可验证需求和异常；建立追踪；比较基线；分析影响、备选与范围 |
| 输出 | 需求草案或变更建议、验收条件、待决策项及获授权的记录 |
| 质量检查 | 编号稳定；来源真实；复合需求只确认批准部分；不伪造会议 |
| 用户确认 | 业务规则、范围和基线变化由用户批准；不得替用户决定 |
| 下一阶段 | 相关范围足够明确，必要决策完成；不等于代码修改获授权 |
| 信息不足 | 列出选择、推荐和影响；核心歧义未解决则停止相关实现 |
| 允许跳过 | 已有有效需求且任务不改变规则时，可复用并记录“不涉及需求变更” |
| 风险记录 | 未决子范围、假设及其对验收的影响，不能默认为已批准 |

### S3 原型设计

| 要素 | 规则 |
| --- | --- |
| 触发与输入 | 页面、交互或导航变化；输入已明确需求、路由、布局及既有原型 |
| 步骤 | 映射页面与需求；设计正常、加载、空、失败和权限状态；使用模拟数据；准备核查步骤 |
| 输出 | 必要原型、交互说明、差异与评审问题，不必每次制作完整网站 |
| 质量检查 | 页面与组件区分；链接有效；不调用真实业务接口；模拟与真实结果分开 |
| 用户确认 | 重要交互、范围变化和原型评审结论由用户确认 |
| 下一阶段 | 交互足以支持设计或实现；未完成浏览器检查不得声称已验收 |
| 信息不足 | 采用明确标注的草案或询问，不假设不存在的页面 |
| 允许跳过 | 无UI变化，或有效既有原型可复用；简单提示修复可用局部交互说明替代 |
| 风险记录 | 跳过的视口、状态、浏览器及拟补充验证 |

### S4 系统总体设计

| 要素 | 规则 |
| --- | --- |
| 触发与输入 | 新系统、跨模块、架构或外部边界变化；输入需求、现有架构与运行约束 |
| 步骤 | 确定模块职责、依赖、权限、数据流及外部资源；比较方案；提前识别测试环境和风险 |
| 输出 | 与范围相称的架构说明、模块边界和设计追踪 |
| 质量检查 | 设计覆盖需求；不虚构现有层次；安全、兼容和部署边界明确 |
| 用户确认 | 技术栈变化、新外部服务、重大架构选择和范围扩大需确认 |
| 下一阶段 | 主要边界足够明确；引用S7提前准备测试策略 |
| 信息不足 | 记录假设并核查；关键依赖未知则不推进有风险的实现 |
| 允许跳过 | 架构不变的局部任务可引用既有设计，不强制重写总体设计报告 |
| 风险记录 | 复用范围、未评估依赖及触发重新设计的条件 |

### S5 系统详细设计

| 要素 | 规则 |
| --- | --- |
| 触发与输入 | 具体业务、接口或数据逻辑需要改变；输入需求、代码、架构和相关原型 |
| 步骤 | 设计输入输出、校验、状态转换、事务、兼容与失败路径；同步S7设计边界测试 |
| 输出 | 局部设计、涉及文件和接口/数据影响、实施与回滚考虑 |
| 质量检查 | 设计满足需求且可测试；不把具体实现选择误写成新增业务规则 |
| 用户确认 | 业务歧义、新迁移、破坏性兼容变化和方案超出授权时确认 |
| 下一阶段 | 核心逻辑与测试目标明确，进入S6仍需实现授权 |
| 信息不足 | 做最小只读实验需符合授权；否则标待核实，不擅自选有业务影响的方案 |
| 允许跳过 | 文档或只读诊断无实现时不必完成；微小修复可用简短局部方案替代独立报告 |
| 风险记录 | 未设计的边界及补偿检查；不得无方案直接改复杂状态逻辑 |

### S6 编码实现

| 要素 | 规则 |
| --- | --- |
| 触发与输入 | 获得明确实施授权；输入目标、必要设计、测试方案、允许修改文件和限制 |
| 步骤 | 保留用户已有修改；复用现有系统；最小范围编辑；同步获授权的文档；静态检查差异 |
| 输出 | 实际修改、需求映射、检查结果及未解决问题 |
| 质量检查 | 不夹带重构；不写秘密；不越权改数据、基线或执行Git |
| 用户确认 | 原请求明确授权的普通修改不逐文件重复询问；扩展或风险变化必须重新确认 |
| 下一阶段 | 修改完成且可进入S7验证；未验证不得称功能已通过 |
| 信息不足 | 停止受影响修改，保留已完成成果并说明阻碍，不用猜测填补规则 |
| 允许跳过 | 只读诊断、纯规划、用户只要求文档或暂不授权实现时跳过 |
| 风险记录 | 明确“未修改代码”，以及目标与现状仍存差异 |

### S7 测试设计与验证

| 要素 | 规则 |
| --- | --- |
| 触发与输入 | 设计阶段提前制定测试；实现后执行；输入需求验收、设计、已有测试和环境 |
| 步骤 | 编码前列正常、异常、权限、边界和回归用例；确认安全环境；获授权后执行；记录实际证据 |
| 输出 | 测试方案、真实执行记录、缺陷与未执行清单 |
| 质量检查 | 预期与实际分开；单元、集成、浏览器和原型模拟分别统计；不以构建替代功能验收 |
| 用户确认 | 真实数据、外部服务、并发/性能负载或新测试环境需核对授权 |
| 下一阶段 | 符合相关验收，或真实报告失败/受限并进入授权的S8或有限交付 |
| 信息不足 | 未配置环境则记录未执行/受限和人工步骤，不假造通过 |
| 允许跳过 | 无运行对象的文档任务可只做文档检查；用户暂缓测试则报告不可宣称验收完成 |
| 风险记录 | 缺失的测试层次、环境和覆盖范围，建议补测与限制 |

### S8 问题修复与回归

| 要素 | 规则 |
| --- | --- |
| 触发与输入 | 缺陷、测试失败或诊断任务；输入复现材料、当前代码、历史证据和范围 |
| 步骤 | 尝试复现并区分历史证据；分析根因、最小方案与回归范围；授权后转S6/S7；判断是否关闭 |
| 输出 | 缺陷分析、方案、实际修复和回归状态，或仅诊断结论 |
| 质量检查 | 无法复现不等于无缺陷；未回归不关闭为已验证；不重复制造无意义修改 |
| 用户确认 | 只要求诊断时修改需另授权；基线冲突转S2；破坏性操作另确认 |
| 下一阶段 | 回归证据支持关闭，或明确遗留原因后进入S9报告 |
| 信息不足 | 提供最小补充材料清单及可行安全检查，停止越权实验 |
| 允许跳过 | 无缺陷任务不适用；诊断任务可跳过修复和回归执行但必须说明 |
| 风险记录 | 未复现、未修复、未回归分别标记，保留影响范围 |

### S9 交付与维护

| 要素 | 规则 |
| --- | --- |
| 触发与输入 | 阶段结束或明确交付/维护请求；输入成果、检查证据、遗留问题和授权 |
| 步骤 | 核查可运行/可用说明、文档一致性和敏感信息；报告结果；仅在授权时提交、推送或部署 |
| 输出 | 交付清单、使用说明、真实版本状态、风险与下一步 |
| 质量检查 | 不声称未执行的发布、审批或验收完成；不倒造开发历史 |
| 用户确认 | Git提交/标签/推送、外部部署与维护数据操作核查单独授权范围 |
| 下一阶段 | 阶段报告后按用户停止点等待；用户已授权连续任务则仅在授权范围内继续 |
| 信息不足 | 发布受限如实区分本地成果与远程状态，不强推或反复造提交 |
| 允许跳过 | 每项任务至少有阶段报告；完整部署材料可按任务不适用或用户暂缓 |
| 风险记录 | 未交付项目、未验证环境、操作责任和后续建议 |

## 3. 质量门

| 门 | 检查内容 | 不满足时 |
| --- | --- | --- |
| G0 范围与证据 | 用户目标、任务类型、允许动作和真实资产明确 | 做安全核查或询问，不猜测权限 |
| G1 需求与基线 | 相关需求可验证；冲突及需批准事项已处理 | 停止受影响设计/实施，其他独立分析可继续 |
| G2 必要设计 | 与任务规模匹配的交互、接口、状态及兼容方案 | 补充局部设计，不机械要求全部文档 |
| G3 测试准备 | 实施前已有验收与回归方案、环境和数据边界 | 先设计用例；未获授权的运行不执行 |
| G4 实施授权 | 代码、基线、数据库和外部操作分别有权限 | 停在分析或方案，不能相互替代授权 |
| G5 结果验证 | 记录真实结果、失败及未执行项 | 不写通过；修复授权不明时先报告 |
| G6 交付与外部动作 | 成果一致、敏感信息检查、提交/部署授权 | 仅交付本地报告，不自行提交发布 |

## 4. 授权矩阵

| 动作 | 执行规则 |
| --- | --- |
| 项目内只读检查 | 在任务范围内可执行；避免输出凭证、个人数据；读取不产生修改授权 |
| 静态分析、构建、测试 | 核查命令及其缓存、网络、写入和数据副作用；在已授权范围执行，不一律称只读 |
| 代码修改 | 用户明确实施请求可以构成授权；只分析、规划或需求确认不构成授权 |
| 正式需求基线修改 | 需明确批准变更范围及版本处理，保留真实记录；代码修改授权不能替代 |
| 数据库迁移或数据修改 | 需明确目标环境、范围、备份/恢复和风险；不得默认操作真实业务库 |
| Git暂存、提交、标签、推送 | 只有本轮明确授权才执行，精确范围、检查敏感信息和已有状态；不继承历史任务权限 |
| 部署、SMTP及外部服务 | 先确认目标、账号、网络/费用/真实消息和数据影响；不擅自发送或公开发布 |
| 破坏性操作 | 必须核查确切目标和授权，优先可恢复方式；不得默认强推、删库或覆盖用户文件 |

## 5. 裁剪、跳过与阶段报告

区分不适用、复用已有成果和用户主动暂缓。记录跳过阶段、理由、依据、受影响需求、风险、补偿检查及重新进入条件。前端提示修复可不重写总体设计，但仍保留问题证据、最小方案、必要测试和授权。

不得补写虚假的跳过阶段成果。每阶段结束报告完成事项、证据、未执行事项、遗留风险与下一步；用户要求逐阶段确认则停止等待。真实结果评价见[评价标准](软件开发Skill评价标准.md)。
