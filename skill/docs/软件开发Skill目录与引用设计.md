# 软件开发Skill目录与引用设计

## 1. 结构选择

采用一个入口、九个阶段参考文件和两个公共参考文件。相比15.1草案进一步细化阶段路由，这是设计演进，不表示此前六类参考文件方案已经部署。本轮不创建以下目录及文件。

```text
skill/
├─ README.md                         # 现有课程目录说明
├─ docs/                             # 已有准备文档及本轮设计文档
└─ software-development-workflow/     # 计划中的正式源码包
   ├─ SKILL.md
   └─ references/
      ├─ 项目启动与需求理解.md
      ├─ 需求分析与变更管理.md
      ├─ 原型设计.md
      ├─ 系统总体设计.md
      ├─ 系统详细设计.md
      ├─ 编码实现.md
      ├─ 测试设计与验证.md
      ├─ 问题修复与回归.md
      ├─ 交付与维护.md
      ├─ 质量门与确认规则.md
      └─ 输出模板与证据规范.md
```

正式包共12个Markdown文件。暂不增加scripts、assets、agents或空目录；后续存在具体可复用需求时再评估。目录名与入口中的name应一致，中文参考文件使用UTF-8和相对引用；跨平台发现及路径处理仍需实际验证。

## 2. 入口职责

`SKILL.md`的YAML头部提供必需的name和description。description应说明适用任务和触发场景，不只写“软件开发助手”。正文包含任务识别、输入检查、阶段选择、核心边界摘要、参考文件路由以及阶段报告与停止规则。目标是可快速读取的简洁入口，不复制所有阶段步骤。

初始版本标识放在正文中；不擅自把version定义为必需的顶层YAML字段。可选界面元数据或调用策略文件不属于本期必需内容，不能为凑结构而创建。

## 3. 参考文件职责表

| 文件 | 何时加载 | 负责内容 | 不重复维护的内容 |
| --- | --- | --- | --- |
| 项目启动与需求理解.md | 所有任务启动，轻任务可精简执行 | 项目资产、用户目标、任务边界、证据与裁剪计划 | 不重复完整授权矩阵 |
| 需求分析与变更管理.md | 新需求、基线冲突、确认或变更 | 需求表达、来源、优先级、确认、追踪和变更影响 | 不复制各项目全部需求 |
| 原型设计.md | 页面或交互需要设计 | 页面映射、状态、导航、模拟边界和评审 | 不将HTML模拟当作真实系统验证 |
| 系统总体设计.md | 架构、模块或跨系统边界变化 | 架构、职责、依赖、数据流及方案取舍 | 局部功能不强制重写总体设计 |
| 系统详细设计.md | 新增或修改具体业务逻辑 | 接口契约、数据操作、状态、事务和失败路径 | 测试模板引用测试阶段文件 |
| 编码实现.md | 已明确授权实施 | 最小修改、现有代码复用、差异与实现追踪 | 不自行批准需求、数据库或Git操作 |
| 测试设计与验证.md | 设计阶段提前加载，验证阶段再次使用 | 用例、环境、安全数据、执行记录、回归和限制 | 不把静态检查当作运行测试 |
| 问题修复与回归.md | 缺陷诊断或回归失败 | 复现、根因、最小方案、关闭条件 | 具体修改和测试分别引用编码、测试文件 |
| 交付与维护.md | 阶段交付、部署或维护任务 | 启动说明、交付清单、遗留风险、获授权的Git与发布操作 | 授权条件统一引用质量门文件 |
| 质量门与确认规则.md | 启动及操作范围变化时 | 授权、阶段门、阻塞、裁剪、跳过与风险记录 | 不维护具体业务规则 |
| 输出模板与证据规范.md | 需要形成计划、设计、测试、交付等成果时 | 统一字段、状态、来源、追踪和报告模板 | 不重复每阶段工作步骤 |

## 4. 引用约束

所有阶段参考文件与入口的引用形成浅层关系：入口直接列出各参考文件；阶段文件可引用两份公共规则及确有依赖的阶段文件，不形成“必须顺序递归阅读全部文件”的链条。每个引用写明读取目的。

共同规则只有一个权威位置。入口可以概括“未经授权不修改、未执行不写通过”，但详细条件只在质量门文件维护。输出字段和证据等级只在输出规范维护；阶段文件引用模板而非另造一套。

源码中的项目特定示例必须标注示例，不能把当前D盘路径、BLOG编号或Vue技术栈作为所有项目的前置条件。课程验证任务放在本设计文档及后续验证记录中，不要求通用Skill依赖课程仓库的全部材料。

## 5. 输出与证据规范的拟定内容

该参考文件后续应提供精简模板：任务边界、需求条目、变更影响、局部设计、测试计划/用例、执行记录、缺陷、阶段交付。公共字段至少包含对象编号或名称、来源、目标、当前行为、确认状态、实现状态、验证状态、证据路径和遗留问题。

区分五类表述：代码静态证据、真实执行记录、用户明确决定、设计建议、待确认/未验证。已有文件的路径可引用，计划文件只能写“拟创建”，不能使用无效链接冒充已交付材料。证据不得包含密码、Token或真实个人隐私。

测试编号使用项目已有规范；没有正式用例时标注待分配，不虚构已存在的测试编号。阶段报告固定回答完成了什么、依据是什么、没有执行什么、有哪些风险、下一步是否需要确认。

## 6. 编写与检查顺序

1. 编写公共质量门和输出规范，固定术语及状态。
2. 编写九阶段文件，每个文件完成触发、输入、步骤、输出和退出条件。
3. 编写入口，按[总体设计](软件开发Skill总体设计.md)映射任务类型。
4. 检查所有相对引用、名称、规则唯一归属和包内自足性。
5. 按[部署设计](软件开发Skill部署与调用验证设计.md)准备后续发现验证；未经授权不安装。
6. 按[评价标准](软件开发Skill评价标准.md)区分结构检查与真实调用检查。

具体阶段字段和授权语义以[阶段规则与质量门](软件开发Skill阶段规则与质量门.md)为准。
