# 软件开发Skill总体设计

## 1. 文档定位

本文件为15.2结构与执行规则设计稿，供用户检查和15.3编写正式Skill使用，不是已安装的Skill。本轮未创建入口文件、阶段参考文件或部署副本。设计依据为15.1四份准备文档、现有项目代码、SRS v1.0.0及已有原型验证记录。

本项目先完成网站开发，后补充需求、原型和Skill资产。后续只能通过真实的新任务、诊断、变更及交付验证Skill，不得倒写为Skill指导了网站最初开发。现有正式需求基线BLOG-REQ-BL-001及Git标签requirements-v1.0.0不因本方案发生变化。

## 2. 名称、定位与边界

推荐名称保持为`software-development-workflow`，共29个字符，只含小写英文和连字符，符合当前创建指南的命名约束。无需更名。

采用“一个主Skill＋九阶段参考文件＋两份公共规则参考文件”。适用于新功能、缺陷修复、需求变更、只读诊断和项目相关文档编写，不作为所有文字写作或所有问答的通用触发器。用户说明和过程成果使用中文，标识、必要命令和元数据使用英文。

设计文件状态为“15.2待用户检查”；正式Skill初始版本建议为`v0.1.0`，在入口正文记录，不把它误认为SRS版本或已建立的新需求基线。版本号的具体维护方式见[部署与调用验证设计](软件开发Skill部署与调用验证设计.md)。

## 3. 核心工作模型

任务进入后先确定：任务类型、授权范围、现有证据、需求基线、允许写入位置、允许执行的检查、阶段停止点。再给出裁剪后的工作路径，不机械执行全部九阶段。

输入至少包括用户请求、项目位置、已知约束和可获得材料；基线、代码、设计、测试等不存在时必须记录缺口，不能假定存在。输出应说明完成事项、实际证据、未执行事项、风险、下一步及需要用户决定的内容。

需求、设计、实现、测试之间应建立可追踪关系。通用Skill使用项目自己的编号和目录约定，不强制所有项目使用BLOG前缀、当前项目路径、五个站点配置键或当前技术栈。项目特定规则通过读取项目资料获得。

## 4. 任务类型与裁剪路径

阶段编号S1—S9见[阶段规则与质量门](软件开发Skill阶段规则与质量门.md)。S7包含编码前的测试设计和编码后的执行验证，并不是必须等编码结束才阅读的文件。

| 任务类型 | 推荐路径 | 必须保留的边界 |
| --- | --- | --- |
| A 新功能开发 | S1理解→S2确认→必要的S3/S4/S5设计→S7测试设计→获得实现授权后S6→S7验证→S9交付 | UI变化才需要原型；架构未变化可以复用既有总体设计；需求确认不能代替实现授权 |
| B 缺陷修复 | S1范围确认→S8复现、根因及最小方案→必要的S5局部设计与S7测试设计→授权后S6→S7回归→S8关闭判断→S9报告 | 只要求诊断时停在方案；无法复现应报告证据限制，不能声称已复现 |
| C 需求变更 | S1→S2核查基线、冲突与影响→等待范围批准→更新获授权的设计与需求材料→S7测试设计→另有实现授权才进入S6→S7/S9 | 未获批准不改基线；批准范围、文档写入和代码修改授权分别核查 |
| D 只读诊断 | S1读取证据→按需S2或S8分析→报告与建议 | 不自动进入S6，不因找到修复方法而修改文件 |
| E 文档编写 | S1识别目的和真实性边界→读取对应阶段证据→编写→一致性检查→报告 | 不是新增的第十阶段；涉及正式基线修改时仍经过S2确认门 |

用户已明确要求实施某项修改，且范围、风险和边界清楚时，该请求可以构成相应修改授权，不必对每个普通文件编辑重复询问。若用户要求分阶段确认、只诊断、只规划，必须遵守停止点。范围外操作仍需单独确认。

## 5. 资产职责与加载方式

入口负责识别任务、选择阶段、提醒不可绕过的授权与证据规则，并指向参考文件。公共质量规则集中管理授权、阶段门和跳过机制；公共输出规则集中管理模板、证据和状态表达；九阶段文件只描述各阶段的工作方法。

入口先读取，公共质量规则在任务启动时读取，阶段文件按实际路径加载；需要输出对应成果时加载输出规范。不要求一次读取全部参考文件，也不允许因按需加载而跳过必要的测试设计或授权检查。目录职责详见[目录与引用设计](软件开发Skill目录与引用设计.md)。

## 6. 项目应用与真实性要求

当前项目有15个已接入末级路由页面，11个独立HTML原型；页面、布局、页签和抽屉不能混为一个统计口径。后端存在Controller直接使用Mapper的实现，不能为了套用分层模板虚构并不存在的Service。SQL、接口和测试范围均应以实际文件为证据。

SRS共80项，本期79项，BLOG-NF-012窄屏专项增强为后续候选；这不等于删除现有响应式布局。原型第一轮浏览器验证已有记录，但不得作为今后Skill运行的验证结果。原型文章管理成功提示残留问题仍可作为真实诊断材料，是否修复需另行授权。

用户已暂缓完整总体设计、详细设计、全面测试材料及全面差异修复。Skill仍须具备这些能力；未来局部实现不能借“完整文档暂缓”而省略必要的局部设计和测试方案。补充回顾性文档应明确时间顺序，不伪造访谈、会议或审批。

## 7. 实施与验收安排

15.3建议先编写两份公共参考文件，再编写九阶段参考文件，最后编写简洁入口并检查引用与格式。正式编写不自动包含安装、运行验证或Git提交。

发现、调用及同步方案见[部署设计](软件开发Skill部署与调用验证设计.md)；结构、过程、成果三个层面的判定见[评价标准](软件开发Skill评价标准.md)。本文件不报告任何Skill已被发现、调用或通过验证的结果。
