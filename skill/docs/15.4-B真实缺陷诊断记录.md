## 6. 根因与代码证据

| 位置 | 当前逻辑 | 对问题的作用 |
| --- | --- | --- |
| HTML第3行 | 主页面 `#feedback` 与抽屉 `#articleErrors` 是独立节点 | 两个提示通道不会自动互相覆盖 |
| 第44行 `note()` | 写入主页面反馈文本并切换error样式 | 主反馈只有显式调用才改变 |
| 第99—109行 `openArticle()`，尤其第108行 | 重置部分表单状态、清空articleErrors并打开抽屉 | 没有清理上一轮主页面成功提示 |
| 第110—126行 `saveArticle()` | 收集校验结果及模拟失败结果 | 新提交可以失败，但主反馈未同步重置 |
| 第121—122行 | 追加outcomeError，更新articleErrors；存在错误立即return | 失败只显示抽屉错误，保留旧feedback |
| 第124—125行 | 无错误后才写入模拟数据、关闭抽屉、渲染并note成功 | 解释首次成功文本来源；失败不进入此写入分支 |
| 第62—67、84—98行渲染函数 | 更新文章、计数和分页 | 不负责清理feedback |
| 第74行通用data-close处理 | 仅调用对应dialog.close() | 取消并不清理主反馈；不能把关闭等同于状态重置 |

已证实的根因是**提示状态生命周期不完整**：上一次成功写入主反馈，新操作打开及失败提前返回均未清理或替换它；抽屉错误更新的是另一个节点，因此两种语义并存。动态DOM观察与上述静态控制流一致。

这不是本轮证据所支持的网络请求故障或异步竞态结论：当前保存逻辑为本地同步模拟，没有发现需通过定时器修复的证据。
