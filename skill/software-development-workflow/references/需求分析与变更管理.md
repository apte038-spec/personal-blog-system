# S2 需求分析与变更管理

## 触发与输入

用于新功能、业务规则冲突、需求确认或基线变更。输入真实用户决定、需求清单、有效基线、验收标准和现状证据。既有需求有效且任务不改变规则时可复用并记录“不涉及需求变更”。

## 工作步骤

1. 核对需求来源、版本、批准范围和实现证据，区分“系统目前怎么做”与“已批准应当怎么做”。目标已被基线覆盖的实现差异可作为缺陷；不能只凭代码不存在就判定新需求。
2. 按角色、触发、正常与异常路径梳理功能、非功能和业务规则，形成可验证验收。沿用项目编号，不虚构历史记录或正式分配。
3. 比较目标与基线，分析页面、接口、数据、权限、历史行为、设计、测试和交付影响。技术字段或注解存在不表示对应业务能力已获批准。
4. 对实质冲突列出备选、推荐及代价。复合请求分别标记已批准、未决或后续候选部分，不以一部分确认扩大整体范围。
5. 获得相应授权后才更新需求、基线登记及追踪，保留真实决定和版本关系；代码实现另经G4判断。后续候选不代表删除已有能力。

## 输出与质量检查

使用[输出模板与证据规范](输出模板与证据规范.md)中的需求、变更和追踪字段，交付需求草案或变更建议、验收条件、影响分析、待决策项或获准记录。检查编号、术语、来源与批准子范围一致，建议不写成已批准，不伪造访谈和会议。

## 退出与信息不足

按[质量门与确认规则](质量门与确认规则.md)检查G1。相关范围明确且必要业务决定完成后，进入适用设计或测试准备；需求确认不自动授权编码。核心歧义未解决时停止受影响实施，记录假设、验收影响与补充材料。基线冲突不能用“立即实现”代替范围和语义核查；已有明确批准可直接复用，不重复请求同一决定。
