# 输出模板与证据规范

需要形成计划、需求、设计、测试、缺陷或交付成果时读取本文件。按任务选用字段，可以合并为简短文字或表格，不要求每次创建独立文档。授权和阶段状态统一见[质量门与确认规则](质量门与确认规则.md)。

## 1. 公共字段与事实分类

成果应能定位：对象编号或名称、来源、目标、当前行为、确认状态、实现状态、验证状态、证据路径、遗留问题。无对应内容时注明原因；没有正式编号则使用对象名称或“待分配”，不虚构已存在的需求、变更或测试编号。

| 信息类别 | 应提供的证据与措辞 |
| --- | --- |
| 代码静态证据 | 文件、符号或行位置及观察；可称“存在该逻辑”，不能称“运行通过” |
| 真实执行记录 | 时间、环境、操作、预期、实际、结果和日志或截图；仅覆盖实际执行对象 |
| 用户明确决定 | 真实请求或确认记录、日期及批准子范围；不能改称教师审批或用户验收 |
| 设计建议 | 目标、理由、备选、假设与影响；标明建议，不能冒充现状 |
| 待确认或未验证 | 缺失事实、影响、补充方式；不能将猜测补成事实 |

来源→需求→验收→原型或设计→实现→用例→执行或缺陷→版本应尽可能关联。只记录本任务相关链路，缺项如实标明。确认、实现、验证分别表达，例如“需求已确认／代码未修改／测试未执行”，不用一个“完成”合并三者。

现有文件使用可访问的路径和有效链接；计划文件写“拟创建”及拟定位置，不用无效链接冒充交付。包内文档引用使用相对路径；项目成果按用户和项目约定定位。报告不得包含密码、Token、SMTP授权码或真实个人隐私，必要证据脱敏后保存。

历史记录注明原日期、对象和环境；新记录使用真实执行时间，不倒填。回顾性文档明确编写时点，不能伪造早期访谈、会议、审批、测试或Skill指导开发的历史。

## 2. 任务边界与阶段计划模板

- 对象与目标：任务类型、项目位置、当前行为、期望结果、来源。
- 范围：允许读取、允许写入、允许检查、明确排除、有效授权依据、阶段停止点。
- 证据与缺口：已有材料、尚未核查事项、影响关键决策的未知项。
- 路径：选用阶段、必要质量门；裁剪原因和复用证据按公共质量规则记录。
- 拟交付物与验收：结果名称、位置或呈现方式、验收条件、待用户决定的事项。

## 3. 需求与变更模板

需求条目字段：编号或名称、真实来源、角色与触发、前置条件、目标行为、业务规则、正常及异常路径、可验证验收、优先级及其依据、确认状态、实现状态、验证状态、关联证据、遗留问题。

变更影响字段：变更名称或已分配编号、现行基线及依据、当前行为、拟改变行为、理由、批准子范围、页面与接口影响、数据与权限影响、历史兼容、设计与测试影响、备选与风险、待决定事项、获准后的版本与追踪更新计划。申请、批准、实施、验证分别记录；草稿不填写虚假批准人或日期。

## 4. 局部设计与追踪模板

设计字段：关联需求及验收、现状证据、方案与取舍、受影响文件或模块、输入输出契约、校验、权限、状态转换、数据约束、事务与并发、异常及反馈、兼容和迁移、回滚考虑、测试目标、未决事项。只填写适用项并解释重要的不适用项。

追踪表字段：需求编号或名称、来源及批准范围、验收条件、设计位置、实现位置、用例编号或待分配、执行状态与证据、关联缺陷、版本。版本分别说明需求基线、成果版本和真实提交；未执行Git时不编造提交标识。

## 5. 测试计划、用例与执行模板

测试计划字段：目标与范围、关联验收、适用层次、环境和工具、安全数据、前置条件、执行授权、副作用和清理、回归范围、进入及结束条件、未覆盖项和风险。

用例字段：编号或名称、关联需求、测试层次、前置状态、输入数据、操作步骤、预期结果、清理方式。编码前形成预期；后补测试应如实说明时间顺序。

执行记录字段：用例名称、实际时间、对象及版本、环境、实际命令或操作、预期、实际观察、结果、日志或截图位置、缺陷、限制。只在确已取得时填写客户端、模型、版本或提交信息。

执行结果使用 **通过、失败、未执行、环境受限、不适用**：通过需本次实际证据；失败保留实际观察；未执行说明原因；环境受限写明已做与未做部分；不适用说明与任务的关系。统计按层次和单位分开，交代计划数、实际执行数及各状态，不能把检查包、用例、断言或截图混算。

格式检查、静态分析、构建、单元、集成、浏览器、原型模拟、真实数据库、真实邮件、性能和用户验收分别记录。构建成功不证明功能验收；Mock不证明真实投递或事务；旧截图不证明本次复现。阶段状态与执行结果不能互相代替。

## 6. 缺陷模板

字段：编号或名称、来源、影响对象与需求、环境、复现步骤、预期、实际、复现证据或未复现原因、影响程度、已证实根因或待验证假设、最小方案、授权依据、实际修改、回归范围与结果、遗留问题、关闭依据。

分别标注“未复现／已复现”“未修复／已修改”“未回归／回归通过或失败”；只有证据支持才称已验证关闭。仅诊断也可形成完整成果，但不能称已修复。

## 7. 阶段交付模板

1. 完成了什么：实际新增或修改、交付路径、与目标的关系。
2. 依据是什么：读取的关键来源、真实检查或运行证据及结果。
3. 没有执行什么：未执行、不适用、环境受限和用户暂缓分别说明。
4. 有哪些风险：未决规则、缺失验证、遗留缺陷及影响范围。
5. 下一步：建议动作、是否已有授权、需要用户决定的具体事项或本阶段停止点。

评估Skill时分别报告结构有效性、流程遵循和成果质量。结构合格或任务结果成功均不能独自证明Skill已被发现、加载或正确执行；需要后续真实调用证据，不把旧项目成果计为本次Skill验证。
